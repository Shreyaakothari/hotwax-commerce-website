{# The measured desktop LCP element. Every number in this comment was measured in a browser on the live page, and the measurement log lives on the PR rather than here. Two defects live today. The img carried loading="lazy", which delays the request for the one element that decides the score, and it was served at full size, 3,746,124 bytes or 3,658 KiB. Why resize_image_url rather than a width attribute. HubSpot does not automatically resize an image over 4096px in either dimension, and this upload is 5721 x 2674, so a width attribute could not shrink it. A width attribute is also what makes HubSpot inject a srcset after render, and srcset beats src, so an attribute would take the resize decision away from this line. The documented remedy for an image over the limit is to resize it explicitly. Why no width or height attribute, which reverses two earlier attempts on this branch. This module renders two different hero sizes, because module.js sniffs the user agent to add a "safari" class and module.css then sets width: -webkit-max-content on the wrapper for it: normal browser: 690 by 400 CSS px, clamped by the theme global img max-width: 100% Safari: 1433 by 670 CSS px, sized off max-height: 62vh with the clamp not binding A width attribute is a presentational hint and no author CSS overrides it here, so any value collapses whichever layout is larger. width="600", which the live field's max_width produced, measured 600 by 400 in both, down from 1433 by 670 on Safari. No single value avoids that. Why the picture element. The wrapper is display:none below 991px, and display:none does NOT stop an img fetch, so making this eager would download the full image on every phone for an element that never paints. Measured: an eager img in this wrapper at a 430px viewport fetched 165,072 bytes with offsetWidth 0. The source media query is evaluated by the preload scanner, so a phone selects the 1x1 placeholder and fetches nothing, while desktop keeps the eager high priority fetch that the LCP fix needs. Measured at 430px: not fetched, 0 bytes. The 991px breakpoint here must stay in step with the display:none breakpoint in module.css. Why 2100 and not more. Safari renders 1433 CSS px wide but 483 of them are off-screen and unreachable, since body is overflow-x: clip and documentScrollWidth stays at the viewport width, so the visible hero is about 950 CSS px. 2100 covers that at DPR 2 and covers the normal 690 box out to DPR 3, at 165,072 bytes against 3,746,124 today. Sizing for the full 1433 would cost 280,018 bytes to render pixels nobody can see. Nothing reserves the box here on purpose. Measured with the image unloaded, .hero-image is already 690 by 400 while the img reports 0 by 400, so the grid reserves it and nothing shifts. An aspect-ratio would fight height: 100%, max-height: 62vh and the Safari rule. No inline style either. The dead sizeAttrs string this replaces carried height: auto, and module.css sets height: 100% on this img inside the 991px query, so printing that style would have changed the rendered size. Note for reuse: fields.json ships a different default image at 5899 x 4529, ratio 1.30 rather than 2.14. The 2100 above is sized for the hero the home page actually uses. #}
